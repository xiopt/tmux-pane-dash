## Isolated command discovery

`clean-room.sh` required and preserved the absolute tmux executable, gave
OpenCode only synthetic HOME/XDG/npm/Bun/TMPDIR state, and used a unique
non-default tmux socket. The temporary OpenCode configuration resolved the
exact global config entry:

```json
{"plugin":["@xiopt/pane-dash-opencode@0.1.0"]}
```

The bounded non-provider candidate is:

```text
opencode run --command noop --print-logs --log-level DEBUG
```

It initializes an OpenCode instance and reaches the command handler without a
provider. Its present bounded result is an expected `UnknownError` for the
unconfigured `noop` command.

This is partial Task 1 empirical evidence, not the final authoritative release
gate. On Darwin, the exact OpenCode process and descendants ran under a
temporary Seatbelt policy (SHA-256
`132b3871c6f774162189bb239f3f5ef2bd255536566386e4e3e9328caf7d5e5c`). Before
OpenCode started, the same policy produced these typed canary outcomes:

```text
non-loopback-connect=denied-by-policy
non-loopback-connect-errno=EPERM
loopback-registry-connect=succeeded
synthetic-root-write=succeeded
forbidden-sibling-write=denied-by-policy
```

The rerun verifies the network policy at the kernel utility boundary: the
sandboxed `/usr/bin/nc -v -z -w 1` loopback probe exited zero, while the
non-loopback probe returned the exact `Operation not permitted` diagnostic,
recorded above as `EPERM`. The runner accepts only `EPERM` or `EACCES`
(including their exact platform message spellings); connection-refused,
timeout, and unreachable-network outcomes fail the gate rather than being
recorded as policy denials.

The policy denies `network*` except loopback inbound/outbound and Unix-socket
outbound, and denies writes except the synthetic clean-room roots and required
`/dev` targets. Unsupported platforms fail closed rather than reporting this
result.

## Registry and cache investigation

The temporary package's `npm pack` cache was separate from the clean-room npm
cache consumed by OpenCode. With scoped `.npmrc` entries pointing only at the
loopback registry, OpenCode 1.17.20 requested exactly two metadata and two
tarball routes, once each:

```text
/@opencode-ai%2fplugin
/%40opencode-ai%2Fplugin/-/plugin-1.17.20.tgz
/@xiopt%2fpane-dash-opencode
/%40xiopt%2Fpane-dash-opencode/-/pane-dash-opencode-0.1.0.tgz
```

The prior missing-tarball conclusion was incorrect: the observed misses were
OpenCode npm-cache hits across the bootstrap/observation runs. The companion
metadata uses the matching `1.17.20` version and the packed plugin exposes both
`.` and `./server` from `dist/index.js`. `audit=false` and `fund=false` prevent
non-package npm routes; any extra or public route fails the spike.

## Load, status, and cleanup result

The exact clean-room command printed:

```text
name=@xiopt/pane-dash-opencode rawSpec=0.1.0 status=PASS cleanup=PASS public-network-requests=0 real-home-writes=0 default-tmux-uses=0
```

The plugin first published nonempty status and a fresh ten-digit Unix-epoch
heartbeat while the wrapper held the first direct synchronous cleanup call.
The shell remained alive with `exec cat` after OpenCode exited. The wrapper
then released and recorded exactly one direct `set-option -pu` call for each of
`@pane_dash_status`, `@pane_dash_status_since`, `@pane_dash_heartbeat`,
`@pane_dash_title`, and `@pane_dash_model`; all five options were absent while
the pane still existed. The runner then terminated the pane/server and verified
that its isolated tmux session and server no longer existed.

`public-network-requests=0` is scoped to the enforced non-loopback denial plus
the exact loopback registry inventory above; it is not a claim about unrelated
host processes. The wrapper log routed every plugin `tmux` invocation through
the unique `-L` socket, so `default-tmux-uses=0` is derived from commands rather
than ambient environment. No production endpoint override or real-home write
was observed.
